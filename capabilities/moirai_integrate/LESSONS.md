# Lessons: moirai_integrate

- [L-0e661662] integrate_validate env_import runs the moirai venv's own Python (moirai_env.sh puts moirai-venv/bin first on PATH), so a pass does not prove the app's separate venv (elmerfold: openfoldenv) can import moirai. openfoldenv has no moirai/dftracer; both venvs are CPython 3.13.2 from the same anaconda base. Exposing the moirai venv's whole site-packages via PYTHONPATH would shadow openfoldenv's typing_extensions/packaging/setuptools; use a directory with only moirai, dftracer, dftracer_utils, pydftracer.

- [L-3c4447cf] moirai_env.sh appends the moirai venv's moirai/lib64, dftracer/lib64 and dftracer/lib to LD_LIBRARY_PATH. dftracer/lib64 holds a generic libyaml-cpp.so.0.6 that shadows the system one, so any flux batch or nested flux instance started from a shell with that environment dies in its broker: 'sched-fluxion-resource: undefined symbol _ZN4YAML6detail9node_data12empty_scalarB5cxx11E', 'flux modprobe rc1 Exited'. The addition is also unnecessary: the moirai binding, moirai-service and dftracer_service carry RPATH/RUNPATH ($ORIGIN/../dftracer/lib64 etc.). Never submit flux batch, or run Maestro with nested: True, with those directories on LD_LIBRARY_PATH; strip them after sourcing moirai_env.sh. Check with a tiny nested-instance job.
