# Lessons: repro_package

- [L-10bc9789] repro_build has no mode for a Maestro/flux-nested study such as BioTox: with biotox-prov it chose mode 'generic' and produced a package that cannot reproduce the run. (1) config.ini pins MOIRAI_SPEC=moirai==0.1.0 and 02_setup_env.sh pip-installs it; the PyPI project named moirai is an unrelated project, the real one is built from a local clone or git+ssh. (2) 04_run.sh puts <moirai site>/moirai/lib64, dftracer/lib64 and dftracer/lib on LD_LIBRARY_PATH: those folders hold a generic libyaml-cpp that breaks every Flux instance (lesson L-3c4447cf). (3) 04_run.sh starts moirai-service on the login node, but traced runs go to compute nodes. (4) COMMAND_smoke/COMMAND_baseline are the session's own submit commands and point at the session's provenance/runs/<stage>/launch.sh, which is not in the package. (5) Nothing creates the biotox-env (python/3.12 module, requirements.txt plus the missing `ply`, maestro), the run copy of the YAML (PEP_NSTRUCT, AF3_INPUT_DIR, step walltimes) or the clean-LD submit; the bank (the user has no ibtap association) is not a config value. (6) The patch holds the annotated tree but not those run-copy edits. A BioTox package needs a workload-specific builder (workload_biotox) or a Maestro mode; repro_verify would cost another ~45 min of one node plus queue wait, so build the mode first. Do not run repro_verify on the generic package.

- [L-fdeaa132] yaml_step blocks bake the moirai Python found when annotate ran as a last-resort fallback (_MOIRAI_PY='/p/lustre5/<user>/.../moirai-venv/bin/python'), so the annotated tree and any patch made from it carry a user path in each block. repro_build's lint does not look at patches/, so a generic package leaks it. A package must blank that fallback (the launch script exports MOIRAI_PYTHON, which is checked first) and lint patches/ too. Also: the job-id lint flags any 'f' plus nine or more alphanumerics in a script, and a `grep -q` or `head` after a pipe under `set -o pipefail` can fail a script with SIGPIPE.

- [L-766eca81] A tool call that sleeps about 590 s or more in the foreground can be killed (exit 137). The repro_verify wrapper job then ends with 'Terminated' and cancels its Flux batch: isolated verification run 1 was cancelled (CA) at 25 minutes, while the study was still in af3_msa. The package was not at fault. Poll a long repro_verify with sleeps of 270 s or less and check `flux jobs <batch id>`; a batch in state CA with the log ending 'Terminated' means rerun. repro_verify needs isolation_root (e.g. /p/lustre5/haridev/biotox/repro_verify) plus scale smoke, and runs as a background job.

- [L-c732c424] Publishing a corrected Elmerfold package into a name already published (elmerfold-v2, created minutes earlier by this session): repro_publish_package refuses an existing target, and the tool environment denied my rm -rf of that folder, so I asked and did not retry or work around. Auto mode took "I remove it myself", so the folder stays until the user removes it. Better order: do not publish the package before the in-place verification passed; publish the package only once the checker and expected.json are final, or publish under a fresh name.

- [L-511ec720] Elmerfold re-published after "capture parameters everywhere": the in-place verification of the package (smoke, 38 activities) reported ok false because prov_check compares entities and edges for exact equality (393/780 vs expected 58/152), but a run that captures inputs and attributes (self.pipeline.start_time, cpu_mem, ctx pointers) has run-dependent entity and edge counts (two identical baselines: 1079 and 1184 entities). Fix staged as proposal 6da9ad26ab95: expected.json stores entity types, prov_check requires activities exact + types present + dangling 0 and treats entity/edge counts as informational. Also graph_compare compared a plain file with itself (absolute outputs_created) -> 0 members, science_unchanged inconclusive, graph stage not advanceable (proposal b11787101b83). Until both are applied the package cannot be published as verified; baseline traces were published first (provenance-traces/elmerfold-v2/20261108_215102). Order after approval: rebuild package, re-publish package (publish refuses an existing target: the stale elmerfold-v2 package must be replaced, ask before removing it), repro_verify in place, publish the verification traces, permissions, publish validate.

- [L-4c091313] Publishing never deletes: always publish a new version. When repro_publish_package refuses an existing target (Elmerfold elmerfold-v2, a stale package) the user answered "no do a v3" and added "by default never delete always creat new versions". Publish under the next free version name (elmerfold-v3 next to v2; traces folders are already timestamped) and leave the old folder untouched, even when the stale one is the session's own. repro_publish_plan/package refuse an existing target anyway, so plan with the next free version name, show that version name in the repro_publish_plan before publishing, and do not ask the user for deletion permission or to rm -rf the old folder.

- [L-6c397f31] Elmerfold final publish (app elmerfold-v4, user's order "never delete, always create new versions"): the reference traces behind expected.json must come from the same annotation as the package. After re-annotating, refresh the moirai_smoke traces (copy the in-place verification raw traces to provenance/traces/moirai_smoke/raw, old ones moved aside, moirai_run_attach of the verification batch, moirai_validate 10/10), then repro_build (expected.json now holds 56 types incl. .input/.attribute), publish_package, repro_verify in place (ok true: activities 38, 389 entities vs 393 expected, edges 780), publish baseline and verification traces, permissions, publish_validate 9/9. Left behind unchanged: elmerfold-v2 (package + baseline traces) and elmerfold-v3 (package).

- [L-ab74044d] Elmerfold elmerfold-v5 was published (package, baseline traces 20261109_161802, verification traces 20261109_162818, repro_publish_validate 9/9, in-place verify ok true with 402 entities vs 393 expected) without refreshing the moirai_smoke reference traces, so expected.json still takes its types from the older smoke reference and lacks the new raw_msa.attribute type (the check passes because extra types are allowed). Rule from the earlier v4 lesson still applies: after a re-annotation that adds attributes/types, refresh provenance/traces/moirai_smoke from the in-place verification (moirai_run_attach, moirai_validate 10/10), then repro_build, so expected.json lists the new types; otherwise tell the user it is not yet in it. Never delete: v5 was a new version next to v2 to v4, which were left untouched.
