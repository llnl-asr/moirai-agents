# Lessons: moirai_run

- [L-60845a5f] A flux batch job's return code does not reflect its `flux bulksubmit` chunk jobs: run.sh ends normally even when a chunk fails, so the batch is COMPLETED rc 0 and the wrapper job exits 0 (false pass). After `flux watch`, read the batch `#flux: --output` file for `exited with exit code <non-zero>` or a line ending ` failed`, and check hosts.txt exists and is non-empty.

- [L-2c18c81c] User decision: a traced BioTox run that finished outside moirai_smoke_run is attached to its stage (moirai_run_attach, built as a capability_update of moirai_run) instead of being rerun for 75 min of node time. The tool must derive the result from flux (INACTIVE + COMPLETED + returncode 0) and from check_study's result.json, never accept a caller-supplied rc, and moirai_validate's exit_0 stays strict.

- [L-fae7d814] A BioTox run submitted by hand with `flux batch launch.sh` (after biotox_run_script and biotox_run_check) completes and writes valid traces (batch f3iKMXkX8ykB: 1 service trace, 0 spill, 28 entities, 16 activities, 11/11 types) but moirai_validate fails with "ran: the run has not started" because the stage's outputs hold no job: moirai_validate reads stage outputs.job, which only moirai_smoke_run / moirai_baseline_run record. Submit BioTox traced stages through moirai_smoke_run(command=<the flux batch + wait command>) so the job is recorded, or give moirai_run a way to attach a finished external flux batch (proposed, not built). Check trace content with moirai_trace_inventory regardless.

- [L-c0c21105] moirai_run_attach works on a real BioTox batch: moirai_run_attach(stage=moirai_smoke, flux_job_id=f3iKMXkX8ykB, output_file=<run dir>/flux-<id>.out, result_json=<run dir>/result.json) returned rc 0 from flux (INACTIVE, COMPLETED, returncode 0) with 1 trace file, and moirai_validate then passed 10/10 (1 service trace, 0 spill, 28 entities, 16 activities, 11/11 types). A proposal approved in the panel may already be applied when capability_apply is called ("already applied"): check the error text, do not treat it as a failure.

- [L-ad8924c0] Checking a finished flux-batch baseline (Elmerfold re-run f3j1LWswZWoZ, 466 s, rc 0): moirai_run_status needs both pipeline and stage ("baseline"); called without stage it raises a TypeError. Cheap order that worked after "is the baseline done?": `flux jobs -n -o '{id} {status} {result} {returncode} {runtime}' <id>` and the tail of run.out, then moirai_run_status(stage baseline), then a failure count in run.out (grep ' failed' / 'exited with exit code [1-9]' = 0), hosts.txt vs prov_<host> files in raw/, and the number of result tars, then moirai_validate (10/10). Trace entities rose from 242 to 1079 with the same 190 activities after attributes and captured inputs were added: report that as expected growth, not as a problem.

- [L-921c44a4] Elmerfold 12 h, 32 node live run started from chat (live pipeline elmerfold-live-32n-20261109-140945, parent elmerfold-prov-20261030-125944, batch f3j9BPvr1Agw, pbatch tlimit 1d, -t 720, 31 chunks of 31n_100ks + 1 launch node): sequence pipeline_new(kind=live, parent), moirai_wrapper_write(stage=live_run) (works for the live stage), elmerfold_run_script into a new run dir with submit_script=<live traces>/submit_moirai.sh, elmerfold_run_check 8/8 (nodes 32), moirai_batch_plan(stage=live_run, limit 43200), moirai_live_run(batch_script, queue, limit, service_venv). Only 9 pbatch nodes were free at submit, so it queues (state SCHED, 32 nodes); the live run uses the working annotated tree, not the published package. The user's "patch queue" was read as pbatch.




- [L-550a4f95] Design rule from the user: a Flux submission must be independent of the web server (it has a timeout and restarts): batches of live and baseline runs are submitted detached (own session, clean env), nothing cancels them on TERM, and run state is read from flux by the recorded flux job id, so a server restart changes nothing. Staged as a moirai_run capability_update.

- [L-aa7a6eec] moirai_live_run must not cancel a live batch when its follower is terminated. Incident: the 12 h, 32 node Elmerfold live batch f3j9BPvr1Agw was CANCELED while still queued (SCHED from 14:10:13, never ran, runtime 0; exception type=cancel by the user's uid at 15:26:27, 76 min later) when the web UI server restarted. moirai_run_status showed the live job "lost" with log tail "Terminated", while the live stage still read "running". Root cause: the batch wrapper that moirai_live_run starts (flux batch ...; flux watch; trap cleanup TERM INT -> flux cancel $jid) is a child of the web UI server process (python -m moirai_agents.webui.server, started about 15:26:20), and its trap cancels the flux job on TERM/INT, so restarting that server (or stopping the tool-server process holding the wrapper) cancels every queued or running live batch. No second job existed when the user said "it got killed again" (flux jobs and the pipeline's jobs dir showed only that one). Say so before submitting long runs until fixed. Workaround used, with the user's standing approval of the 12 h / 32 node / pbatch run: submit directly and detached with `env -i HOME USER TERM bash -lc 'module load mpifileutils/0.11.1 && flux batch -t 720 --queue pbatch <run.sh>'` (batch f3j9zUsgjby9, 32 nodes), which survives any server restart; attach the finished job later with moirai_run_attach. Needed capability change (diff for a thread that can read tool.py, 68 KB; a capability_builder agent could not, capability_get returns ~120 KB with the code as one escaped line): (1) _wrapper(live=True) (stage live_run): trap on TERM/INT only logs "follower stopped; flux job $jid keeps running" and exits 0, no flux cancel (line ~314 cleanup() keeps cancel for smoke/baseline); (2) launch the live wrapper detached (start_new_session=True, stdin DEVNULL), record jid, live and follower pid in the job record; (3) moirai_run_stop runs flux cancel <jid> itself, then kills the follower; (4) moirai_run_status with a dead follower and a RUN/SCHED job reports "following lost, job still RUN/SCHED" and re-attaches a follower, with a gone job writes the final state to the stage; (5) checks: live wrapper has no flux cancel in the trap, non-live keeps flux cancel and exit 143, stop calls flux cancel (fake flux on PATH); (6) SKILL corner case and Corrector line.

- [L-ed87bc84] Detached submit confirmed in use: Elmerfold baseline-4 (moirai_baseline_run, batch mode, pdebug, 60 min, 2 nodes) returned flux_job_id f3jABdfAUsBm at 4 s with flux_state queued; state was then read from flux (`flux jobs -n -o '{id} {status} {result} {returncode} {runtime}'` in loops of at most 280 s: RUN at 264 s, COMPLETED rc 0 at 491 s), moirai_run_status gave done/rc 0 and moirai_validate 10/10. While it ran the 12 h, 32 node live batch f3j9zUsgjby9 stayed RUN (200 s in at the end) across the web server activity, i.e. the independence rule held. Order for 'run the baseline and check' after a re-annotation: move provenance/traces/baseline aside (baseline_before_<reason>), moirai_wrapper_write(stage baseline, service_venv), elmerfold_run_script into a NEW run dir (moirai-baseline-4), elmerfold_run_check 8/8, moirai_baseline_run, wait on flux, moirai_run_status + moirai_validate.

- [L-e3c19e79] A queued live batch reads the working annotated tree when it starts, not when it was submitted (Elmerfold 32 node live batch f3j9zUsgjby9, SCHED, 32 nodes, runtime 0, while the annotation was edited for gaps G-71ce0cb0 and G-9e3bd857 and annotate_apply ran). So re-annotating while a live batch is queued silently changes what that run traces. Before annotate_apply with a live batch in SCHED (flux jobs), say so to the user and ask whether to apply now or after the batch starts; after annotate_apply, note the batch will pick up the new annotation.

- [L-196265bb] Long-running checks must be detached from the chat session: tool calls and background agents that wait on a heavy read (repro_publish_data_validate on 31 live trace files, 2.96 GB) were killed whenever the session restarted ("exit 137", agent "didn't finish before the previous session ended") and the user saw "not progressing". Started the equivalent check as `nohup setsid .venv/bin/python` (core/provtrace.read(<published raw>, workers=16), then compare with the published run.json counts) writing /g/g92/haridev/v8_live_validate.log, and told the user to look at that log. Rule: for anything longer than about 4 minutes, start a detached process with a log file, report the log path and the expected duration, and poll with calls under 60 s.

- [L-c07389f2] A live run started from the Live Run view arrives with chosen inputs and a rendered command (Elmerfold 64n: INCHUNKS=64n_100ks, QUEUE=pbatch, LIMIT_MIN_baseline=720). When the message says "show me the exact command, limit and queue and ask me before starting", show them in ask_user (stage live_run, confirm Start/Change), end the turn, and call moirai_live_run only after the answer is Start. The user then answered Start; afterwards validate and publish_data (repro_publish_traces, repro_publish_data_validate).

- [L-5f840223] Live start of the published elmerfold-v4 package (scripts/04_run.sh) failed in 2 s with rc 127: $VENV/bin/python (OUTPUT_ROOT/env = /p/lustre5/haridev/elmerfold-provenance/env) does not exist; OUTPUT_ROOT holds src, traces, work, moirai_env.sh, submit_moirai.sh but no env/ or moirai-venv/. 04_run.sh needs 03_build.sh (setup-env.sh --use-rocm7) to have built the venv first. Before moirai_live_run on a package command, check that $VENV/bin/python and the wrapper exist; if not, ask the user to run the build (compute node) instead of starting.
