# Lessons: moirai_run

- [L-60845a5f] A flux batch job's return code does not reflect its `flux bulksubmit` chunk jobs: run.sh ends normally even when a chunk fails, so the batch is COMPLETED rc 0 and the wrapper job exits 0 (false pass). After `flux watch`, read the batch `#flux: --output` file for `exited with exit code <non-zero>` or a line ending ` failed`, and check hosts.txt exists and is non-empty.

- [L-2c18c81c] User decision: a traced BioTox run that finished outside moirai_smoke_run is attached to its stage (moirai_run_attach, built as a capability_update of moirai_run) instead of being rerun for 75 min of node time. The tool must derive the result from flux (INACTIVE + COMPLETED + returncode 0) and from check_study's result.json, never accept a caller-supplied rc, and moirai_validate's exit_0 stays strict.

- [L-fae7d814] A BioTox run submitted by hand with `flux batch launch.sh` (after biotox_run_script and biotox_run_check) completes and writes valid traces (batch f3iKMXkX8ykB: 1 service trace, 0 spill, 28 entities, 16 activities, 11/11 types) but moirai_validate fails with "ran: the run has not started" because the stage's outputs hold no job: moirai_validate reads stage outputs.job, which only moirai_smoke_run / moirai_baseline_run record. Submit BioTox traced stages through moirai_smoke_run(command=<the flux batch + wait command>) so the job is recorded, or give moirai_run a way to attach a finished external flux batch (proposed, not built). Check trace content with moirai_trace_inventory regardless.

- [L-c0c21105] moirai_run_attach works on a real BioTox batch: moirai_run_attach(stage=moirai_smoke, flux_job_id=f3iKMXkX8ykB, output_file=<run dir>/flux-<id>.out, result_json=<run dir>/result.json) returned rc 0 from flux (INACTIVE, COMPLETED, returncode 0) with 1 trace file, and moirai_validate then passed 10/10 (1 service trace, 0 spill, 28 entities, 16 activities, 11/11 types). A proposal approved in the panel may already be applied when capability_apply is called ("already applied"): check the error text, do not treat it as a failure.

- [L-ad8924c0] Checking a finished flux-batch baseline (Elmerfold re-run f3j1LWswZWoZ, 466 s, rc 0): moirai_run_status needs both pipeline and stage ("baseline"); called without stage it raises a TypeError. - [L-550a4f95] Design rule from the user: a Flux submission must be independent of the web server (it has a timeout and restarts): batches of live and baseline runs are submitted detached (own session, clean env), nothing cancels them on TERM, and run state is read from flux by the recorded flux job id, so a server restart changes nothing. Staged as a moirai_run capability_update.

- [L-aa7a6eec] moirai_live_run must not cancel a live batch when its follower is terminated. Incident: the 12 h, 32 node Elmerfold live batch f3j9BPvr1Agw was CANCELED while still queued (SCHED from 14:10:13, never ran, runtime 0; exception type=cancel by the user's uid at 15:26:27, 76 min later) when the web UI server restarted. moirai_run_status showed the live job "lost" with log tail "Terminated", while the live stage still read "running". Root cause: the batch wrapper that moirai_live_run starts (flux batch ...; flux watch; trap cleanup TERM INT -> flux cancel $jid) is a child of the web UI server process (python -m moirai_agents.webui.server, started about 15:26:20), and its trap cancels the flux job on TERM/INT, so restarting that server (or stopping the tool-server process holding the wrapper) cancels every queued or running live batch. No second job existed when the user said "it got killed again" (flux jobs and the pipeline's jobs dir showed only that one). Say so before submitting long runs until fixed. Workaround used, with the user's standing approval of the 12 h / 32 node / pbatch run: submit directly and detached with `env -i HOME USER TERM bash -lc 'module load mpifileutils/0.11.1 && flux batch -t 720 --queue pbatch <run.sh>'` (batch f3j9zUsgjby9, 32 nodes), which survives any server restart; attach the finished job later with moirai_run_attach. Needed capability change (diff for a thread that can read tool.py, 68 KB; a capability_builder agent could not, capability_get returns ~120 KB with the code as one escaped line): (1) _wrapper(live=True) (stage live_run): trap on TERM/INT only logs "follower stopped; flux job $jid keeps running" and exits 0, no flux cancel (line ~314 cleanup() keeps cancel for smoke/baseline); (2) launch the live wrapper detached (start_new_session=True, stdin DEVNULL), record jid, live and follower pid in the job record; (3) moirai_run_stop runs flux cancel <jid> itself, then kills the follower; (4) moirai_run_status with a dead follower and a RUN/SCHED job reports "following lost, job still RUN/SCHED" and re-attaches a follower, with a gone job writes the final state to the stage; (5) checks: live wrapper has no flux cancel in the trap, non-live keeps flux cancel and exit 143, stop calls flux cancel (fake flux on PATH); (6) SKILL corner case and Corrector line.

- [L-29619559] User: "the index should be fast. What is going on?" Finding on the 64 node Elmerfold live run (130 files, 4.3 GB): the index is fast (done in minutes); the slow, heavy part is provtrace.read turning TraceViewer rows into Python records: 63.9M records, 1.9M activities, 8.1M entities, 39.2M edges, 4.9M relations, 60 types, 0 dangling, 729 s with 8 then 4 reader workers at ~3.8 GB RSS each. The BrokenProcessPool was a native "std::system_error: Resource temporarily unavailable" (thread creation EAGAIN): each spawned reader worker holds 150-180 native TraceViewer threads, so 8 workers plus other sessions of the user (11292 of ulimit -u 16384 threads in use, load 113 on a shared login node) hit the limit; the new fallback halved the workers and succeeded. A moirai_run_status/validate on a run this size should not rebuild the whole Python graph on each call: cache counts by trace dir stamp, or read counts with TraceViewer aggregates (count by name) and only build the graph when needed; and cap native threads per worker.
