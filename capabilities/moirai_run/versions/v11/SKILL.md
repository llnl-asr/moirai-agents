# Run with moirai

## Rules
- `moirai_smoke_run` first, same small test as the smoke stage. If the original passed and this fails, the annotation is the suspect.
- Before the baseline, the gate must settle what runs, where, at what scale, for how long. Use `ask_user`, then `moirai_baseline_run` with exactly that.
- While it runs, follow it with `moirai_run_status` and tell the user the Dashboard is live. Then `moirai_validate`.
- A flux batch belongs to Flux, never to the web server or a tool-server process. Batch mode submits DETACHED (see the batch bullets) and records `flux_job_id`; after ANY server restart or timeout, the first thing to do for a stage that shows a batch job is `moirai_run_status(pipeline, stage)`: it reports the real flux state (queued / running / completed / failed / cancelled / timeout / lost), not a process of the server. Only `moirai_run_stop` cancels a batch, by an explicit `flux cancel <recorded id>`; never cancel on a signal, never as a side effect of a restart.
- Submit through `moirai_smoke_run` / `moirai_baseline_run` / `moirai_live_run` whenever they can run the app. Use `moirai_run_attach` ONLY for a flux batch that was submitted externally (BioTox: `biotox_run_script` + `biotox_run_check`, then `flux batch launch.sh` by hand, the approved BioTox flow) and has already FINISHED. Never attach a run that is still going, and never use it to skip a run the pipeline could submit.
- Attach: `moirai_run_attach(pipeline, stage, flux_job_id, output_file, result_json)`, stage `moirai_smoke` or `baseline`. `output_file` is the batch `--output` file (its tail is copied into the job log); `result_json` is the `check_study.py` output of the run dir. It records the stage's `outputs.job` as a finished job with `source: attached` (job record, log and rc file in the pipeline's own jobs dir; traces `<work>/traces/<stage>/raw`, `mode: attached`) and then `moirai_validate` judges it like a started run. The rc is DERIVED, never given: `flux jobs -n -a -o '{state} {result} {returncode} {runtime}' <id>` (retried three times), state must be INACTIVE, rc 0 only for result COMPLETED and returncode 0; with `result_json` its boolean `ok` must be true too (false: rc 1 and the problems are at the end of the job log). Unknown or unfinished flux job, other stage, unreadable file: an error and nothing is written. Then `moirai_validate`; tell the user the job was attached and where the rc came from.
- Attached runs have no wrapper `hosts.txt`. In `moirai_validate`, a stage without `hosts.txt` skips `host_traces` (nothing to compare with). For an attached run the per-host evidence comes only from the trace inventory: file names `prov_<host>[-spill].pfw[.gz]` (the BioTox service trace). A host with only spill traces fails `host_service_trace`; host names found add a passing `attached_hosts`; no such names: no per-host judgement. `exit_0` is never relaxed: it always uses the job rc.
- Order of use for batch mode (an app launched by a generated `flux batch` run.sh, e.g. Elmerfold; run.sh stays UNMODIFIED):
  1. `moirai_wrapper_write(pipeline, stage, service_venv)`: writes ONLY `<work>/traces/<stage>/submit_moirai.sh` (mode 755; creates the stage and raw dirs; returns the path and the sha256; the same text again changes nothing). It submits and starts nothing. `service_venv` defaults to the venv root of the integrate stage's `moirai.python` and is verified to hold an executable `dftracer/bin/dftracer_service`; the text is identical whether it is passed or defaulted.
  2. `elmerfold_run_script(..., submit_script=<that path>)` (and `cwd`, see `workload_elmerfold`): the generator requires the submit script to exist.
  3. `elmerfold_run_check(..., submit_script=<that path>)`.
  4. `moirai_batch_plan(stage, batch_script=<run.sh>)`: checks run.sh, shows the exact submit command, the `--output` file the post-run evaluation will read (`batch_output`) and whether the wrapper on disk equals the fresh render (`wrapper_on_disk`).
  5. The user's yes.
  6. `moirai_smoke_run` / `moirai_baseline_run` / `moirai_live_run` with `batch_script`, `queue` (default pdebug; pbatch for live), `limit` (seconds; batch gets ceil(limit/60) minutes), and the SAME `service_venv`/`original_script`/`data_dir` as in step 1.
- Before submitting, the run tools compare the wrapper on disk with the freshly rendered text. When they differ (a different `service_venv`, edited by hand, an older render) they REWRITE it and say so (`wrapper.action` = `rewritten`, with both sha256) in the result and the stage note. They still refuse a run.sh that does not reference the wrapper, before writing or submitting anything.
- The wrapper `<work>/traces/<stage>/submit_moirai.sh` is what `flux bulksubmit` runs on the exclusive worker node, once per chunk: `submit_moirai.sh <chunk csv>`. It sources `moirai_env.sh`; exports `MOIRAI_LOG_FILE=<stage>/raw/prov`, `MOIRAI_DATA_DIR`, `MOIRAI_SERVICE_SHM=<base>-${FLUX_JOB_ID:-$$}` (unique per job), `MOIRAI_PC_BLOCKS` (16) and `MOIRAI_PC_FLUSH_MS` (250); resolves `dftracer_service` (see below); appends its host to `<stage>/hosts.txt`; starts `moirai-service start` IN THE BACKGROUND of its own shell (output to `<stage>/service-<host>-<job>.log`); waits up to 60 s for `/dev/shm$MOIRAI_SERVICE_SHM`; on failure exits 3 with a message BEFORE the app (no silent spill); traps EXIT/TERM/INT to run `moirai-service stop` with the same env; runs `bash <original submit_smsp.sh> "$@"` as a child, keeps its rc, stops the service, exits with the rc. The original is the ANNOTATED copy's `monomer-structure-prediction/submit_smsp.sh` unless `original_script` is given.
- dftracer_service resolution in the wrapper, in order: an explicit `MOIRAI_DFTRACER_SERVICE` in the environment wins; else the build-time default printed by `moirai-service --help` when it exists; else the baked resolved path, then `<dftracer package dir>/bin/dftracer_service` where the package dir comes from `python -c 'import dftracer,os;print(os.path.dirname(dftracer.__file__))'` (python on PATH after sourcing `moirai_env.sh` is the venv's), then `<service_venv>/lib/python*/site-packages/dftracer/bin/dftracer_service`. The venv's `moirai-service` is a Python entry-point script: its location says nothing about where dftracer lives.
- The batch SUBMIT job (since 2026-11-09; before, a wrapper watched the batch): `start_detached` runs it as `nohup env -i HOME USER LOGNAME TERM bash -lc 'bash <job>.sh; echo $? > <job>.submit.rc'` in its OWN SESSION (setsid(2) through `start_new_session`), stdin `/dev/null`, output to the job log, clean environment as `repro_package` does, so the login profile provides `module` and `flux`. The script loads `mpifileutils/0.11.1`, checks `dbcast`, runs `flux batch -t <min> --queue <q> <run.sh>`, prints the id, writes it atomically to `<stage>/flux_job_id` and EXITS. It has no `flux watch`, no trap, no `flux cancel`. The job record `<pipeline>/jobs/<job>.json` has `source: flux-batch`, `flux_job_id` (filled by the first status call after the id file appears), `idfile`, `submit_rc_file`, `batch_output`, `hosts_file`, `queue`, `submit_command`; the stage outputs get `flux_job_id` and `flux_state`.
- State and the post-run evaluation are derived from flux, not from a process: `moirai_run_status` and `moirai_validate` call `finish_batch`, which asks `flux jobs -n -a -o '{state} {result} {returncode} {runtime}' <id>`. SCHED/DEPEND/PRIORITY: `queued`; RUN/CLEANUP: `running`; INACTIVE with a result: evaluated ONCE (the first caller after the end, whoever it is, also after a restart), rc file and verdict lines written into the job log. Evaluation (`evaluate_batch`): batch not COMPLETED/0: flux's returncode (124 TIMEOUT, else 1); then the `--output` file (path in run.sh's `#flux: --output` header): rc 6 when not readable; rc 4 naming the failed chunk job id(s) when it has `exited with exit code <non-zero>` or a line ending ` failed`; rc 5 when `<stage>/hosts.txt` is missing or empty; else rc 0. The batch return code does not reflect its bulksubmit chunk jobs (Failure 1), so COMPLETED 0 alone is never success. `lost` only when flux answers that it does not know the id (or the submit ended with no id and no rc); `unreachable` (status `unknown`, `finished` inconclusive) when `flux` cannot be run from the server's shell; `submitting` while the id is not yet recorded.
- `moirai_run_stop` is the ONLY canceller: `flux cancel <recorded id>` when flux says the job is not INACTIVE (queued jobs too); the next status shows `cancelled` (rc 1).
- Exact submit command shape: `flux batch -t <ceil(limit/60)> --queue <queue> <run.sh>` (40 min for the 2400 s smoke). run.sh is never rewritten; the service is never started with `flux run`/`flux submit`.
- `moirai_batch_plan` validates run.sh: exactly one `flux bulksubmit` line, a `:::` input list, the token before `'{}'` is the wrapper path, the annotated tree path appears in run.sh, no old moirai preamble; it warns when run.sh has no `#flux: --output` header (then only hosts.txt is checked).

## Live run (the `live_run` stage of a live pipeline)
- A live run is the long run of an app a run pipeline already annotated, baselined and published: `pipeline_new(kind='live', parent=<run pipeline>)`, then `moirai_live_run`. Many live runs per app; each has its own chat, graph and queries.
- It uses the parent's annotated tree and `moirai_env.sh`; its traces go under `<parent work>/live/<id>/traces/live_run/raw`. Default limit 12 h; ask the user for the real limit and queue.
- Ask before starting it (a gate on the command, limit and queue), then report progress with `moirai_run_status(pipeline, 'live_run')` only when asked or when it stalls: the Live Run view shows the graph forming. A long live batch may sit queued for hours; that is `flux_state: queued`, not a failure.
- When it ends: `moirai_validate(pipeline, 'live_run')`. Spec coverage (`types_seen`) is an assumption here, not a failure: the baseline and the graph diff proved it.

## Constraints
- Traced runs of any size go through a launcher on compute nodes, never on a login node. The tools submit nothing but the one detached `flux batch`; `moirai_wrapper_write` writes one file and nothing else.
- A long batch must not depend on the server process. The web UI / tool server has a timeout and restarts regularly. Nothing that holds a Flux job (queued or running) may be a child of it, wait on it, or cancel it on a signal: no `flux watch` in a server-owned process, no `trap ... flux cancel`, no state kept only in a pid. The job record carries `flux_job_id`, and everything else (state, rc, evaluation) is recomputed from `flux jobs` plus files in the pipeline dir and the stage dir.
- Only `moirai_run_stop` may run `flux cancel`, and only on the recorded id. Selftest `cancel_only_by_stop` and `batch_no_cancel_trap` guard this.
- `moirai_run_attach` submits and cancels nothing: it only runs `flux jobs` (read-only) and writes inside the pipeline's own jobs dir and stage outputs. Do not pass an rc, a status or a made-up job id; do not attach a job the user did not approve or that belongs to another run.
- Ask before more than one node or an hour. `limit` becomes the batch's `-t` (Flux ends it with TIMEOUT, rc 124): set it from what the user approved (2 nodes + Rabbit, 40 min for the Elmerfold smoke). Never allocate more than the user approved.
- Never start moirai-service as a flux job in this app: after the drain, prestage, the dbcast steps and the app job each need the whole worker node (`--exclusive`, `--nodes $num_nodes --tasks-per-node 1`), so a one-core service job blocks them until the limit. Never `dftracer_service start` under `flux run` either: it never returns.
- Do not change `MOIRAI_SERVICE_SHM` by hand: each job has its own ring.
- Do not edit run.sh or the wrapper by hand: regenerate (`moirai_wrapper_write`).
- A batch job's return code is not evidence that the app ran. Judge a batch run by its `--output` file, `hosts.txt`, the service logs and the traces, never by `COMPLETED`/rc 0 alone.

## Corner cases
- Tiny `/dev/shm`: lower `MOIRAI_PC_BLOCKS` in the environment; application and service must agree.
- Only `*-spill.pfw.gz` files: the app did not reach the ring. `moirai_validate` names the hosts that only have spill traces.
- Activities are never aggregated, so an activity in a tight loop grows the trace fast: watch the Dashboard's rate.
- Exit code 124 (or 137): the batch hit `limit` (Flux result TIMEOUT). Plain-command runs: the job runner's timeout.
- `libdftracer_core... cannot open shared object` in the log: `moirai_env.sh` predates the fix or points at another venv; run `integrate_apply` again.
- `moirai-service --help` shows a default `dftracer_service` under `/tmp/<user>/pip-build-env-...` (gone). The real one is `<venv>/lib/python*/site-packages/dftracer/bin/dftracer_service`; the compiled `site-packages/moirai/bin/moirai-service` (not the venv's `bin/moirai-service` entry script) holds `../../dftracer/bin/dftracer_service`. `moirai_service_resolve(venv=...)` finds it and reports `binary_kind`. Pass `service_venv` or let it default.
- Wrapper exit codes: 2 setup problem (original script, env file, moirai-service or dftracer_service missing), 3 ring not visible, 130/143 INT/TERM, otherwise the app's rc. Batch evaluation exit codes: flux's own returncode when the batch failed, 124 TIMEOUT, 4 a chunk job failed, 5 no host ran the wrapper, 6 `--output` unreadable.
- The wrapper text depends on `service_venv`, `data_dir` and `original_script`: a different value at run time than at `moirai_wrapper_write` makes the run rewrite the file (reported). A defaulted `service_venv` renders the same text as the explicit one. The v7 fallback change (python-based resolver) changes the text once: a wrapper written by v6 is reported `rewritten` at the next run.
- `--output` is truncated and rewritten per run, so the file only describes the last run. The evaluation reads at most its last 50 MB.
- A batch started by an older version of this tool (job record without `source: flux-batch`, a wrapper process that watches the batch) is still judged by the old job runner; its `flux_job_id` is in the first line of its log (`batch job: <id>`): `moirai_run_attach` it once it FINISHED, or `flux jobs <id>` by hand while it runs. Do not start a second batch for the same stage while one is queued: check `moirai_run_status` first.
- The server restarted while the stage is `running`: `moirai_run_status` first. `queued`/`running`: nothing to do, report it. `lost`: flux does not know the id (a different flux instance, or the job is older than the flux job-db retention): `flux jobs -a <id>` from the shell that owns the instance. `unknown`: flux is not on PATH of the server's shell.
- Attach: the same flux id attached twice overwrites its own job record (id `attached-<flux id lowercased>`); a different attach to the same stage replaces `outputs.job`, unless the stage's current job is still running (refused). Attached runs have no `hosts.txt` and no `submit_moirai.sh`: `moirai_batch_plan`/`moirai_wrapper_write` do not apply. `moirai_run_stop` on an attached job stops nothing. A BioTox run whose traces are not under `<work>/traces/<stage>/raw` is reported by a warning and fails `trace` in the validator: copy or link nothing by hand, ask for the right directory.
- A COMPLETED rc 0 flux batch with `result_json` ok false is attached with rc 1: for BioTox the batch result alone does not prove the study worked (the same lesson as the bulksubmit false pass).

## Failure 1 (D1): false pass, the batch returned 0 while the chunk job failed
(confirmed 2026-10-30, pipeline elmerfold-prov-20261030-125944, batch job f3hFu78obrzb, wrapper job moirai-smoke-batch-934280540)
- Symptom: the per-chunk wrapper exited 2 (`moirai-wrapper: no dftracer_service found`), the app never ran, yet the batch finished COMPLETED returncode 0 and the wrapper job `moirai-smoke-batch` exited 0. `run.out` (path in `#flux: --output`, here `<elmerfold runs>/moirai-smoke/run.out`) held `flux-job: task(s) exited with exit code 2`, `Fri Oct 30 23:32:42 PDT 2026: f35QqToh9 failed`, `flux-job: there are no more waitable jobs`, `All jobs completed (or failed)!`. A good run has none of the first two.
- Cause: run.sh ends normally even when its `flux bulksubmit` chunk job fails, so the batch rc is 0.
- Fix: the evaluation (`evaluate_batch`, run by `moirai_run_status`/`moirai_validate` when flux says the batch ended) reads `--output` and fails with rc 4 (names the chunk job id, here f35QqToh9), 5 or 6 (see Rules). Verify: `moirai_wrapper_selftest` shows `batch_fail_detected=ok batch_clean_pass=ok batch_hosts_missing=ok`; those run the rendered submit script under bash with a fake flux and then `finish_batch` against this exact failing text and a clean one.

## Failure 2 (D2): wrong dftracer_service resolver
(confirmed 2026-10-30, same run)
- Symptom: `moirai-wrapper: no dftracer_service found (default ... missing)`, exit 2, and the warning `no service venv given and dftracer_service not resolved here`.
- Cause: the fallback resolved `$(dirname "$(readlink -f "$(command -v moirai-service)")")/../../dftracer/bin/dftracer_service`, but `<elmerfold>/moirai-venv/bin/moirai-service` is a Python entry-point script (`#!.../bin/python`, `from moirai.service import main`), not the compiled binary (`site-packages/moirai/bin/moirai-service`); the real service is `site-packages/dftracer/bin/dftracer_service`.
- Fix: `service_venv` defaults from integrate's `moirai.python` (venv root) and `moirai_wrapper_write`/`moirai_smoke_run`/`moirai_baseline_run`/`moirai_batch_plan` raise an error naming the fix when `<venv>/lib/python*/site-packages/dftracer/bin/dftracer_service` is missing or not executable; the wrapper fallback resolves the package through python. Verify: `moirai_service_resolve(venv=<venv>)` returns `path` and `exists: true`; `ls -l <venv>/lib/python*/site-packages/dftracer/bin/dftracer_service`.

## Failure 3 (D3): `the run has not started` for a batch submitted by hand
(confirmed 2026-11-05, pipeline biotox-prov-big-20261104-124916, batch f3iKMXkX8ykB: COMPLETED rc 0 in 4515 s, valid traces in `<work>/traces/moirai_smoke/raw`, `result.json` of check_study.py ok true)
- Symptom: `moirai_validate` fails `ran` with `the run has not started` although the traces are complete.
- Cause: the stage's `outputs.job` is recorded only by `moirai_smoke_run`/`moirai_baseline_run`; the approved BioTox flow submits `flux batch launch.sh` by hand.
- Fix: `moirai_run_attach(pipeline, "moirai_smoke", "<flux id>", output_file="<batch --output file>", result_json="<run dir>/result.json")`, then `moirai_validate`. Verify: the result shows `source: attached`, `rc` 0 and `trace_files` > 0; `moirai_wrapper_selftest` shows the `attach_*=ok` cases (they run against a fake flux).

## Failure 4 (D4): a queued 12 h batch was cancelled by a restart of the web server
(measured 2026-11-09 by the user, Elmerfold live batch f3j9BPvr1Agw: 12 h, 32 nodes; cancelled by the user's uid at 15:26:27, 76 min after submit, while still queued, exactly when the web UI server process restarted)
- Symptom: the flux job is CANCELED while SCHED; the stage stays `running` while `moirai_run_status` said `lost`; no trace, no message.
- Cause: the batch wrapper job was a background child of the tool/web server process (`jobs.start`); it ran `flux batch`, then `flux watch $jid`, with `trap cleanup TERM INT` -> `flux cancel "$jid"`. The server has a timeout and restarts regularly; the wrapper got TERM and cancelled the Flux job. The state was derived from the wrapper's pid, so a restart also made it `lost`.
- Fix (this version): the submit is detached (own session, nohup, `env -i`, stdin /dev/null, output to the job log), has no watch and no cancel trap, records `flux_job_id`, and exits; state comes from `flux jobs` of that id; the post-run evaluation runs from `moirai_run_status`/`moirai_validate` when flux says INACTIVE; `moirai_run_stop` is the only canceller. Verify: `moirai_wrapper_selftest` shows `batch_no_cancel_trap=ok batch_id_recorded=ok status_queued_from_flux=ok finish_after_server_restart=ok status_lost_only_when_flux_unknown=ok cancel_only_by_stop=ok detached_argv=ok`; `moirai_batch_render(...)` `batch_wrapper` contains `never cancels the flux job` and no `trap`/`flux cancel`/`flux watch`; on a real run `moirai_run_status` returns the `flux_job_id`, and `flux jobs <id>` agrees after you restart the server.

## Unconfirmed (state it to the user; nothing below was run)
- Whether `moirai-service start` returns by itself (daemonizes) or stays in the foreground: neither `--help` nor a start was run. The wrapper does not depend on it (background plus ring wait; stop then reaps the pid, kill after 10 s).
- libstdc++ shadowing: `submit_smsp.sh` puts `${ELMER_ENV}/lib` first in `LD_LIBRARY_PATH` (line 110) AFTER the wrapper started the service, so the service is not affected, but the app process loading moirai/dftracer libs may pick the conda libstdc++. Symptom: `GLIBCXX_... not found` in the chunk log. Not tested.
- Trace file names per host: assumed to carry the host name; if not, `host_traces` is inconclusive.
- Whether the GPU inference server runs on the same node as the driver (the one running the wrapper): a server on another node is not traced by this service.
- `flux bulksubmit` environment: assumed to pass run.sh's `ELMER_*` to the wrapper (the original needs them, so the app job already relies on it).
- `moirai_wrapper_write` and the rewrite path were tested only on temp dirs through the pure functions, not on a real pipeline.
- `flux jobs -o {returncode}`/`{result}` and `flux batch -t <min>` are taken from memory, not run here; the batch evaluation was run only against a fake flux.
- The detached submit (`nohup env -i HOME USER LOGNAME TERM bash -lc`, own session) was tested only through its argv and the script under bash with a fake flux; NOT on a real cluster and NOT with a real restart of the web server. Assumed: the login profile provides `module` and puts `flux` on PATH, and the server's shell (where `moirai_run_status` runs) can reach the same Flux instance with `flux jobs -a` (the same assumption `moirai_run_attach` makes). If `flux` is not on PATH in `bash -lc`, the submit job log says `flux: command not found` and the stage fails with rc 1.
- That the user's server restart sends its signal to a process group/session that the detached submit is no longer in (own session, nohup). A restart that kills by cgroup (systemd KillMode=control-group) would still kill it BEFORE `flux batch` returns, but never after (the Flux job does not belong to the server).
- That `flux jobs -a` still lists a finished job long after it ended on this system (job-db retention); otherwise a late status call reports `lost` for a job that completed, and `moirai_run_attach` with the `--output` file is the way to record it.
- That python and `moirai_env.sh`: python on PATH after sourcing `moirai_env.sh` is the venv shim, and that the integrate outputs key is `moirai.python` (flat or nested are both accepted): not run on a real pipeline.
- Other failure lines a real chunk failure can leave in `--output` (beyond the two seen) are not known; a failure that leaves neither pattern still shows as no host / no trace in `moirai_validate`.
- `moirai_run_attach`: the exact output of `flux jobs -n -a -o '{state} {result} {returncode} {runtime}'` (space-separated, `INACTIVE COMPLETED 0 <seconds>`; `-` for empty fields) is taken from the request, tested only against a fake flux; not yet run on the real BioTox batch. The BioTox service trace names `prov_<host>.pfw.gz` are taken from the request, not re-read here.

## Corrector
Predictor `moirai_wrapper_write`, `moirai_smoke_run`, `moirai_baseline_run`, `moirai_live_run`, `moirai_run_attach`, `moirai_batch_plan`, `moirai_batch_render`, `moirai_service_resolve`, validator `moirai_validate` (and `moirai_wrapper_selftest` for the wrapper, detached batch and attach tools). A failed verdict comes here: fix the original tool or its input, then predict and validate again. The same failure twice stops the loop: change approach, or ask.

| Failed check | Correct |
|---|---|
| `ran` (`the run has not started`) | the stage has no job. If the run can still be submitted: `moirai_smoke_run` / `moirai_baseline_run` / `moirai_live_run`. If a flux batch was submitted by hand and has FINISHED (BioTox `flux batch launch.sh`): `moirai_run_attach(pipeline, stage, flux_job_id, output_file, result_json)` (Failure 3), then `moirai_validate` again. Still running: wait, do not attach. Attach refused as unfinished/unknown: check `flux jobs -a <id>` for state and id |
| `finished` inconclusive | the flux job is `queued` or `running` (or `unreachable`): `moirai_run_status` shows `flux_state`; wait, do not restart the run, do not cancel unless the user asks |

## Self-heal
- `exit_0` failed: compare `log_tail` with the smoke stage; failures with `moirai` in them are annotation or link problems.
- `activities` is zero: the app ran from somewhere other than the annotated tree (run.sh `ELMER_SRC_DIR`), or the annotated functions are not reached.
- Service does not start: read the service log (`No space left on device` means the ring).
- `No running server found` on stop: start and stop used different env; the wrapper stops with the env it started with, so check the service log for the host.
- A run that hangs at `Prestage` or `dbcast`: something holds a core on the worker node; `moirai_run_stop` and look for a stray service job (`flux jobs -a`): none should exist in this design.
- The stage says `running` but nothing seems to happen after a server restart: `moirai_run_status` (state from flux), not the Jobs panel's pid view.
- `moirai_run_attach` says the job is unknown: `flux jobs -a <id>` from the same shell (the flux instance that owns the job); an id from another instance cannot be attached.

## Self-learn
- Anything new explored here (workload, software, tool, system) becomes a capability: `capability_builder`, Rules. Elmerfold's run.sh shape, once run, belongs in `workload_elmerfold`; BioTox's launch flow in `workload_biotox`.
- Lesson (2026-10-30, pipeline elmerfold-prov-20261030-125944): the v3 design started moirai-service as pinned `flux submit` jobs after the drain and rewrote run.sh. Dropped because, in the real generated run.sh, the prestage `flux run --nodes $num_nodes --tasks-per-node 1`, the `flux run --exclusive ... dbcast` steps and `flux bulksubmit --nodes 1 --exclusive` all need the whole worker node; a one-core service job there would block them until the limit. The service now lives inside the app job (the wrapper).
- Lesson (2026-10-30): a tool that creates an input another generator demands must be callable before that generator (wrapper_write before run.sh), not only as a side effect of submitting.
- Lesson (2026-10-30, batch job f3hFu78obrzb): a batch job's return code does not reflect its `flux bulksubmit` chunk jobs, because run.sh ends normally when a chunk job fails. A COMPLETED rc 0 batch proves nothing; read its `--output` file (failed chunk lines), `hosts.txt` and the traces.
- Lesson (2026-10-30): a pip venv's `bin/<tool>` is usually a Python entry-point script; derive sibling-package paths from the installed package (`import dftracer`), not from the script's location.
- Lesson (2026-11-05, pipeline biotox-prov-big-20261104-124916): a validator that insists on a job recorded by one launcher fails a good run launched another approved way. When the user chose "attach the finished run", the fix was an attach tool that derives the rc from the scheduler and the study check, not a loosened validator.
- Lesson (2026-11-09, batch f3j9BPvr1Agw): anything long-lived that the scheduler owns must not be owned by a server process. The state of a long job is derived from the scheduler by its recorded id, and post-processing is done by whoever asks after it ended, never by a process that has to survive a restart. A pid-based status turns every restart into `lost`.
- Run settings that worked for this app: `lesson_add`. Settle each Unconfirmed item with the run that proves it (`(confirmed YYYY-MM-DD)`).
- A failure mode the validator missed: `capability_update` with a check for it.
