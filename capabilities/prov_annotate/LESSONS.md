# Lessons: prov_annotate

- [L-47cab606] A shell step of a Maestro YAML (AlphaFold 3, Rosetta) is annotated with mode yaml_step, not by editing the app: the wrapper is an EXIT trap at the top of the step's cmd that calls the root _moirai_prov.py as a script with the moirai venv's Python (MOIRAI_PYTHON, else beside MOIRAI_SERVICE or moirai-service on PATH, resolved before the step activates its own venv). Tie each record to what the step really did with a shell variable the cmd sets (uri "${PDB_FILE}") rather than a fixed path, so an early `exit 0` (peptide_prepack skip when PEP_ID is "-") records nothing; give both sides of a hop the same type and key text (case id $(TARGET)/$(PEP_ID)/seed-$(SEED)_sample-$(SAMPLE)).

- [L-a532f2d2] maestro_dry in annotate_validate is inconclusive, never a failure, when `maestro run --dry` fails on the SOURCE YAML too (a parameter generator such as biotox's gen.py is needed). Pass maestro=<session>/tmp/biotox-env/bin/maestro and maestro_args="--pgen gen.py --pargs inputs:<path> --pargs dock_mode:all --pargs dock_chains:Z --pargs seeds_per_chunk:1" (the arguments of run-biotox.sh) so the dry run can pass; an inconclusive check blocks pipeline_advance.

- [L-8f5af9d7] dftracer_service (moirai-service) is a singleton per trace prefix (MOIRAI_LOG_FILE) per host: a second `start` for the same prefix is refused with 'dftracer_service is already running on <host> (PID ..) for <prefix> — refusing to start a second instance. Run `stop` first', and `stop` from any step stops the one that is running. So in a one-node Maestro study the yaml_step block's own service start is refused (its helper then spills because the step ring it exports does not exist) and its EXIT-trap `stop` kills the conductor's service; every later step's Python hook finds 'no dftracer_service is accepting events on <conductor ring>' and spills. Services that do start write the same prov_<host>.pfw.gz name and overwrite each other. Fix design: in a step block, if the inherited MOIRAI_SERVICE_SHM ring already exists in /dev/shm on this node, reuse it and neither start nor stop; only on a node without it start an own service with a unique ring AND a unique MOIRAI_LOG_FILE prefix (…-step-<id>), and stop only a service the block started. Steps with no yaml_step activity (prepack, analyze) then work through the conductor's ring.

- [L-e860d1f7] annotate_validate maestro_dry fails on a reused BioTox annotation with "No module named 'imp'" (maestrowf/maestro.py:351), even after integrate wrote moirai_env.sh, while the source dry run passes. It is a mask, not a broken wrapper: Maestro loads the parameter generator by file path and does not add the tree to sys.path, so the annotated gen.py's `import _moirai_prov` raises ImportError, and on Python 3.12 Maestro's Python 2 fallback (`imp`, maestro.py:351) then dies after ANY earlier ImportError; the report must show the first earlier exception. Cause: _maestro_dry ran with the tool server's environment. Fix: run maestro_dry with the PYTHONPATH that moirai_env.sh exports, i.e. the moirai shim first, then the annotated root swapped for the temp copy of the annotated tree. The tree alone is not enough: the generated _moirai_prov.py does `import moirai`, which only the shim provides (moirai is not in the app's env). History: v5 (tree only) did not fix the BioTox defect; v6 (proposal 15beaba525ef) does. A check reproduces it with /bin/sh as a fake maestro running a file `run` from the tree. User chose "capability_update with the fix" over a direct edit.

- [L-7b4f3f86] The annotate gate was answered by auto mode without the entity diagram ever being published to the web UI (pipeline_status showed annotate diagrams: 0 although the stage passed): the user later asked "although it says annotate is done where is the link that shows the entity diagram?". Publish it with diagram_publish_annotation (then diagram_check) BEFORE the annotate ask_user, every time, including when the annotation is reused from an earlier pipeline; annotate_diagram only writes provenance/annotation_diagram.md.

- [L-bc306c08] Gap kind missed_inputs: an activity that wraps a callback with no arguments (for example a task's on_finish) captures no parameters, because argument capture sees nothing and the values sit on self, set by a base class constructor (a command string such as run_str). Name them in the spec with capture: {inputs: {label: "self.<attr>"}}; the helper parses command-line flags into the .input entities. When exploring, check every wrap of a no-argument callback for parameters held on self. Before re-annotating a pipeline another chat drives, ask the user, and do not re-run the smoke or baseline without their go.
