# Lessons: capability_builder

- [L-148dcf38] A capability_builder background agent can be stopped by a session end before it stages its proposal: after the user said "done restarted" and "done approve", capability_list showed no pending proposal for repro_package (v10, no output_root in repro_verify). Before telling the user to approve, check capability_list pending for the proposal id, and resume the agent with SendMessage if it is missing. prov_annotate (v13) and workload_elmerfold (v1) were applied by the user's earlier approvals.

- [L-3c35680e] A capability_builder agent was stopped by a session restart twice while staging a whole-file tool_code change for repro_package (116 KB tool.py); user said "continue". To survive restarts, stage in order: first a small capability_update (why + skill_md only) so a proposal exists, then capability_refine it with the large tool_code, then capability_verify; report the proposal id as soon as the first step exists.

- [L-f02b6e0e] The staged-in-order approach worked partly: after restarts the small skill_md proposal for repro_package was applied (v11, rule 'verification never on home' in SKILL.md) but the tool_code step was not staged, so the rule is live while repro_verify still has no output_root. Check tool.py (grep the new parameter) and not only the version number before telling the user a fix is done.

- [L-08e082a0] capability_update proposals are rejected when test code holds literal machine paths (e.g. an /g/g92 or /p/lustre5/u path in a unit check: "machine-specific path ... take paths as arguments"); build such strings from constants (HOME_FS + "/g92/x", LUSTRE_BASE + "/u/x"). capability_refine cannot carry checks, so a change that adds a check needs a full capability_update (tool_code + checks); omit skill_md when the skill is already staged/active.

- [L-282acacd] The third resume of the repro_package tool_code builder succeeded (proposal bba3adeb8a7d, capability_verify clean, 7 checks pass) after the first two were stopped by restarts: when a builder agent is stopped, resume it with a narrowed brief and the current facts (here: the user had removed ~/moirai_repro, so add outputs_gone and a fresh-batch path). The test code must not contain literal site paths (validation refuses them): build them from parts.

- [L-4805ba41] When the user reports a proposal out of date (repro_package at v12 after the earlier approval), read the current tool.py and diff what is already live (grep the new names), then refine on_current with only the missing parts: here outputs_gone and a self-test fix. This produced proposal 268732cd4881 with 7 of 7 checks and kept every v12 addition.

- [L-6a305cdc] User: "No it should have the new validator." The TraceViewer-count change for repro_package (row_counts) never reached tools: grep of capabilities/repro_package shows it only in LESSONS.md, versions are v8/v9. Builder agents on whole-file capability_update changes of a ~120 KB tool.py (capability_get result 222 KB, too large to read) were stopped twice by session/MCP restarts before staging (L-148dcf38, L-3c35680e). Before telling the user a change is live, grep the live tool.py for it; for a change of a few lines in a big tool, capability_update still takes the whole tool_code, so ask whether a direct small file edit is allowed or ask the user not to restart while the builder runs. Capability needed: capability_update with a patch/diff argument (old_string/new_string) instead of the whole tool_code.

- [L-b1e1bac7] Proposal 08ef4a3c5a41 (prov_performance) went out of date because the earlier Python-only proposal b8ddd4679005 was approved first (prov_performance v2: perf_annotate, perf_preview, perf_apply, perf_validate, perf_diagram, perf_annotate_selftest live). When several proposals of one capability are staged, the user approves the one they see first: refine the later ones on_current right after the first is applied, and keep the superseded ones marked so the user does not approve both. The remaining part of 08ef4a3c5a41 is the clang model for C/C++ (extract_functions, R6/R7, threshold 20), C++ insertion and the full skill and checks.

- [L-cc2ec2c8] Staging order worked for the 120 KB repro_package tool.py: skill-only capability_update first (id 29ec1f862aa3), then capability_refine with the whole tool_code. A refine whose sandbox check fails stages nothing (nothing is kept), so the whole text must be resent: write the selftest fixtures with values that cannot overlap (a fake user 'tester' matched '/tester/' inside the fake home '/home-fake/tester', giving two findings instead of one). Final refine id d3fb897f86ea verified clean.
